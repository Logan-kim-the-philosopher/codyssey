# 운영 개선과 트러블슈팅 회고

## 장애 전 누수 탐지
monitor.sh의 RSS 절대값과 증가율을 함께 기록한다. PID와 프로세스 시작시간을 묶어 PID 재사용을 구별하고, 컨테이너 cgroup 한도·사용량·memory.events를 수집한다. 짧은 튐 대신 여러 관측 구간의 지속 증가를 경고하며 남은 메모리/증가율로 예상 한도 도달 시간을 계산한다. 내부 heap 값과 RSS를 나란히 두고 로그 공백·수집 실패를 별도 상태로 표시한다. 이번 자료의 메모리 상승 패턴이 운영 경고 기준을 설계할 근거다. 실제 기준값은 정상 부하 기준선과 서비스 SLO로 결정해야 한다.

## 가장 치명적인 장애와 예방
이 과제의 단일 서비스 응답 관점에서는 Deadlock을 우선 선택한다. PID가 살아 있어 단순 생존 검사에 통과하면서 요청은 무기한 막힐 수 있기 때문이다. 응답 시간·작업 진행률 health check와 락 순서 통일이 필요하다. 다만 공용 서버 전체의 안정성 관점에서는 제한 없는 메모리 누수가 다른 프로세스까지 압박하므로 더 치명적일 수 있다. 영향 범위와 사용자 요청 실패율을 근거로 판단하며 절대 순위를 주장하지 않는다.

## OOM과 Deadlock 동시 발생의 조사 순서
1. 요청 실패·가용 메모리·swap·memory.events를 신속히 확인해 전체 서버 위험을 판단한다.
2. 프로세스 트리, RSS, CPU, 스레드 상태, 마지막 로그를 제한된 시간에 보존한다. 증거 보존 때문에 복구를 장시간 지연하지 않는다.
3. 실제 메모리 고갈이 다른 서비스까지 영향을 주면 자원 제한·트래픽 이동·문제 인스턴스 격리로 영향 확산을 먼저 줄인다.
4. 안정된 복제/격리 환경에서 교착의 자원 의존 관계와 누수 추세를 각각 확인한다. 죽은 PID로는 교착 상태를 조사할 수 없으므로 종료 전 스레드 자료가 중요하다.
5. 변경 변수를 하나씩 통제해 각 장애의 임시 조치와 근본 해결을 검증한다.

## 소스를 수정할 수 있다면
- Memory Leak: 무제한 데이터 누적을 제거하고 캐시·큐 상한과 객체 수명 관리, 장기 soak test를 도입한다.
- CPU Spike: busy loop를 이벤트 대기로 바꾸고 작업 예산·동시성 제한을 둔다. 내부 부하 표시와 실제 CPU 시간 측정을 일치시키며 보호 정책에 연속 초과 시간과 복구 동작을 설계한다.
- Deadlock: 전역 락 획득 순서를 통일하고 임계 영역을 줄인다. timeout·취소 시 자원 정리를 보장하며 경쟁 실행 테스트로 순환 대기를 검출한다.
이 항목은 개선 제안이며 제공 바이너리를 수정하거나 역공학한 결과가 아니다.

## 다시 수행한다면
첫 실행에서 부모/자식 PID를 확인하고 블랙박스 워크로드의 경로 선택을 로그로 점검하겠다. 모든 실행은 별도 컨테이너에서 동일 조건으로 비교하고 실행 중 관측 스크립트를 변경하지 않겠다. ps 누적 평균과 top 구간 사용률, 내부 로그 값을 처음부터 구별하겠다. 종료 원인은 메시지·시그널·관측 종료 표식을 함께 확인하겠다. 낮은 CPU 설정에서는 메모리 누수가 동시에 진행하고 높은 CPU 설정에서는 다른 경로가 실행되므로 환경변수가 워크로드 선택에도 영향을 주는 가능성을 남겨 둔다.

## 측정 한계
유한 관측 기간의 교착 회피와 임계치 미도달은 장기 안정성의 증명이 아니다. 정확한 소스 원인과 실제 CPU 내부 계산식은 바이너리 분석 금지 조건 때문에 확인하지 않는다. 커널 OOM, 일반 SIGTERM, 앱 보호 종료를 각각 구별한다. 검증 파일이 존재하는 것과 실제 검증 기준을 만족하는 것은 다르며 CPU 급상승 항목은 고해상도 관제의 원시 CPU 시간으로 별도 검증한다.
